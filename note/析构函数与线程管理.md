# ~Robot_ctrl() 析构函数 与 jthread 线程管理

## 一、为什么要有 `~Robot_ctrl()`？

**声明位置**：[include/robot_controller/robot_controller.hpp:22](../include/robot_controller/robot_controller.hpp#L22)
**实现位置**：[src/robot_controller/robot_controller.cc:22](../src/robot_controller/robot_controller.cc#L22)

```cpp
// .hpp 中声明
~Robot_ctrl();

// .cc 中实现
Robot_ctrl::~Robot_ctrl() = default;
```

实现只有一行 `= default`，但放在 `.cc` 文件里有深意。

---

## 二、核心原因：控制销毁顺序

`Robot_ctrl` 的成员声明顺序：

```cpp
class Robot_ctrl {
    std::vector<std::jthread> threads;       // ① 第一个声明
    std::shared_ptr<Robot_set> robot_set;    // ②
    Device::Rc_Controller rc_controller;     // ③
    Device::Dji_referee referee;            // ④
    Chassis::Chassis chassis;               // ⑤
    Config::GimbalType gimbal;              // ⑥ 最后一个声明
};
```

**C++ 规则**：成员按**声明的逆序**销毁。

```
声明顺序:  threads → robot_set → rc_controller → referee → chassis → gimbal
          ─────────────────────────────────────────────────────────────→
销毁顺序:  gimbal → chassis → referee → rc_controller → robot_set → threads
          ←─────────────────────────────────────────────────────────────
```

### 为什么 threads 必须最后销毁？

`threads` 里的 `jthread` 析构时**自动调用 `join()`**，阻塞等待线程函数结束：

```cpp
// C++20 std::jthread 的析构行为
~jthread() {
    if (joinable()) {
        join();   // 阻塞，直到线程 return
    }
}
```

如果 threads 先销毁（即 join 先发生），CPU 上的真实线程还在访问 `gimbal`、`chassis`、`robot_set` 等对象。此时这些对象**已经活着**——顺序保证了。

如果 threads 不是最后一个销毁——比如 `gimbal` 在 threads 之后销毁——就会：

```
1. ~gimbal()        ← gimbal 对象被销毁
2. ~threads()       ← jthread.join()
                       线程还在跑 gimbal.task()！
                       但 gimbal 已经没了！
                       → 崩溃
```

## 三、线程 vs jthread：谁属于谁？

### threads 存储的是"控制句柄"，不是线程本身

```cpp
void Robot_ctrl::start() {
    threads.emplace_back(&GimbalT::task, &gimbal);     // jthread 在 Robot 里
    threads.emplace_back(&Chassis::task, &chassis);     // jthread 在 Robot 里
    threads.emplace_back(&Device::Dji_referee::task, &referee); // jthread 在 Robot 里
}
```

```
                        Robot_ctrl
                   ┌─────────────────┐
                   │ threads         │
                   │  ┌───────────┐  │
                   │  │ jthread 0 │──┼──绑定──→ CPU线程A: gimbal.task()
                   │  │ jthread 1 │──┼──绑定──→ CPU线程B: chassis.task()
                   │  │ jthread 2 │──┼──绑定──→ CPU线程C: referee.task()
                   │  └───────────┘  │
                   │                 │
                   │  gimbal   ←─────┼── 线程A读写这个对象
                   │  chassis  ←─────┼── 线程B读写这个对象
                   │  referee  ←─────┼── 线程C读写这个对象
                   └─────────────────┘
```

| | jthread（句柄） | 真实线程 |
|---|---|---|
| 在哪 | `Robot_ctrl::threads` 这个 vector 里 | 操作系统调度队列里 |
| 做什么 | join、detach、控制线程生命周期 | 执行 `gimbal.task()`、`chassis.task()` 等 |
| 归属 | Robot_ctrl 的成员变量 | 不属于任何对象，属于操作系统 |
| 类比 | 遥控器（握在 Robot 手里） | 员工（在车间干活） |

**线程执行的是云台的函数，但控制权在 Robot 手里。**

## 四、实际情况下析构函数不会被正常调用

所有模块线程都是死循环：

```cpp
[[noreturn]] void GimbalT::task() {
    while (true) {      // ← 永远不会 return
        update_data();
        // PID 控制...
        UserLib::sleep_ms(1);
    }
}

[[noreturn]] void Chassis::task() {
    while (true) {      // ← 永远不会 return
        decomposition_speed();
        // 功率限制...
        UserLib::sleep_ms(2);
    }
}
```

所以 `~Robot_ctrl()` 如果真的执行：

```
7. ~threads()
     └─ jthread[0].join()  → 等 gimbal.task() return  → 永远等不到 → 永久阻塞
```

程序实际退出方式：

- 硬件断电（比赛结束关电）
- `exit(-1)` 直接 kill 进程（IMU 离线、电机离线触发）
- 操作系统终止进程

`~Robot_ctrl()` 是一个**防御性占位**——如果有一天需要正常退出，销毁顺序已经排好了。

---

## 五、总结

| 问题 | 答案 |
|---|---|
| 为什么要有 `~Robot_ctrl()`？ | 控制成员销毁顺序，保证 threads 最后被销毁 |
| 为什么 `= default` 放在 `.cc` 里？ | 精确控制析构代码的生成位置，避免每个 include 的翻译单元都生成一份 |
| threads 为什么不放在各模块里？ | jthread 是线程的**控制句柄**，集中管理方便统一退出 |
| 线程执行的是谁的代码？ | `gimbal.task()` / `chassis.task()` ——各模块的成员函数 |
| 线程控制权在谁手里？ | Robot_ctrl，通过 `threads` 里的 jthread |
| ~Robot_ctrl() 实际会被调用吗？ | 比赛中基本不会，线程都是死循环，join 会永远阻塞 |
