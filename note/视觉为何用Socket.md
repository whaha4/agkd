# 为什么视觉自瞄用 Socket 而不是 CAN 或串口？

## 一、硬件拓扑：不是一台电脑

```
┌─────────────────────────┐       ┌─────────────────────────┐
│  主控板（嵌入式 ARM）      │       │  视觉电脑（Jetson / 树莓派） │
│                         │  UDP  │                         │
│  ● 跑 Robot_ctrl        │◄─────►│  ● 跑视觉算法             │
│  ● 接 CAN 总线 → 电机    │ 网线   │  ● 接摄像头 → 识别装甲板    │
│  ● 接串口 → IMU + 遥控器 │       │  ● 算出目标 yaw/pitch     │
│  ● 接 Socket → 收自瞄   │       │                         │
└─────────────────────────┘       └─────────────────────────┘
```

## 二、三种通信的使用场景

| 通信方式 | 连接谁 | 物理介质 | 原因 |
|---|---|---|---|
| **CAN** | 主控板 ↔ 电机 | CAN 总线（双绞线） | 电机只有 CAN 接口，板上通信 |
| **Serial** | 主控板 ↔ IMU/遥控器 | 排线/UART | IMU 和遥控器用串口输出 |
| **Socket** | 主控板 ↔ 视觉电脑 | 网线（Ethernet/WiFi） | 两台独立机器，只有网络互联 |

## 三、为什么视觉不能走 CAN 或串口？

1. **物理上接不了**：视觉电脑（Jetson）是一台带 GPU 的 Linux 主机，它和主控板之间只有网线。主控板上的 CAN 总线控制器是专门的硬件，视觉电脑上没有。

2. **数据量更大**：CAN 一帧只有 8 字节，视觉要传浮点数（yaw、pitch、目标位置等），UDP 一包几百字节直接搞定。

3. **不需要实时性那么极端**：CAN 的优势是微秒级确定性延迟，适合电机电流控制。自瞄数据 10ms 刷新一次就够了，UDP 足够了。

## 四、实际配置

```cpp
// config_sentry.hpp
.auto_aim_ip   = "127.0.0.1",   // 本地测试用 localhost，实战时改视觉电脑的 IP
.auto_aim_port = 11453,         // 视觉发给主控的端口
```

主控端 Socket 监听 `0.0.0.0:11451`，视觉发给主控的 `11453` 端口。两个端口独立：

```
视觉 ──发送──→ 主控:11453（Auto_aim_control 包）
主控 ──发送──→ 视觉:11451（SendAutoAimInfo 包，告诉视觉当前云台角度）
```

## 五、总结

```
通信方式 = 物理连接决定

CAN    → 同一块板子上的设备（电机）
Serial → 同一块板子上的设备（IMU、遥控器）
Socket → 两台机器之间（视觉电脑 ←→ 主控板）
```
